What holds up (verified, not assumed)

  • D3 — the SyncApi boundary is real. Grep-proven: exactly one @supabase/supabase-js import exists in the entire repo (packages/sync-api/src/supabase.ts). The reporter and the phone go through ReporterSyncApi/MobileSyncApi; a PocketBase backend is genuinely a second implementation file.
  • Revision sync survives contact. Server-side event identity (sha256(slug|client|dedup_key)), immutable identity columns with content-only upserts, revision-keyed watermarks, and page-atomic phone pulls were pglite-verified earlier and re-checked in source. The phone advances its watermark only after a SQLite transaction commits.
  • Reporter boundary discipline. No provider credentials are stored; tokscale output is zod-validated against a checked-in fixture (drift fails loudly per D2); token hashing on the phone/reporter side matches the SQL recipe byte-for-byte (tested).
  • Conventions hold everywhere. D8 (UTC + offset stored, never pre-bucketed; phone buckets at render), D6 freshness model in the UI layer, humanize() applied across all identifier surfaces, monochrome theme tokens with semantic colors only for status.
  • Machine dynamics. Nothing in the schema or app hardcodes the machine count; the + add-machine sheet and − confirm-and-cascade removal keep the matrix open (updated matrix is in AGENTS.md).

Real bugs (ranked)

highB1 — D6 quota semantics broken server-side

burn_fetch_quota_latest (0002) returns the freshest snapshot per (provider, account, metric) regardless of status — error rows included. The phone's sync then deletes and replaces its quota mirror from that result, and queryQuotas filters status = 'ok'. Consequence: the first failed vendor fetch (expired token, rate limit) evicts the last good numbers from the UI until a machine succeeds again. This contradicts D6 and the Supabase README ("freshest successful snapshot … diagnostics retained").

Fix shape (SQL-only): distinct on restricted to status = 'ok' for the display channel, plus a separate latest-error query (or an errors array in the same payload) for the diagnostics the UI may surface later.

medB2 — resetDb wipes user preferences

resetDb runs delete from kv, and it is called by connect, disconnect, and "Clear demo data". So every backend reconnect silently resets reporting_timezone (D8: "persisted, stable until changed") and theme_mode back to system defaults. Preferences are not data — the wipe should exempt preference keys (or preferences should live outside kv).

lowB3 — streaks break on zero-session days (by design?)

The 120-day demo yields a 97-day streak because the sparse-start generator emits occasional zero-session days. Defensible semantics (a day with zero AI usage is a break) — recorded so nobody "fixes" it accidentally.

Contract drift (server SQL ↔ mirror schema ↔ SyncApi types)

medC1 — export_schema is half-wired and silently dropped

The server column exists, EnvironmentInfo carries it, parseEnvironmentRow reads it — then the mirror insert throws it away (db.ts's environments table has no such column). The local quota_snapshots mirror lacks its column too. Either persist it or trim it from the type until the burn-events exporter (D2) exists.

medC2 — quota row_key schemes differ between demo and cloud

Demo seed keys env|provider|account|metric; cloud sync keys provider|account|metric. No collision today because the server pre-dedups per metric — but if fetch_quota_latest ever returns per-environment rows, cloud mode collides silently. One scheme should win (demo's env-scoped key is the more precise one).

lowC3 — the export-schema pipeline is aspirational

quotaToWire hardcodes export_schema: 1, the reporter heartbeats exportSchema: null, and EVENT_EXPORT_SCHEMA is exported and never used. Dead until D2's exporter exists — fine, but mark it so nobody trusts it.

lowC4 — the tokscale pin exists in 4 places

version.ts (canonical, used by burn-report init ✓), the reporter configSchema default string, the demo generator's parserVersion literal, and the demo seed's tokscale_version literal. Config default should import the canonical constant; the generator/seed literals are data, acceptable.

Duplication (accepted today, tracked)

  • Per-day bucketing written 4×: buildSeries, queryGranularityMax, queryRecords, queryDailyTotals all walk loadEvents + bucketKey. A single bucketEvents(events, tz) helper collapses them — and time intelligence (roadmap idea #1) will want a 5th copy, so consolidate then.
  • The 28-column usage_events insert exists in 3 shapes: the SQL migration, sync.ts's parameterized cloud insert, and sync.ts's string-built demo insert — plus the mirror schema in db.ts. Adding one column means touching four places with no parity test. Highest-value place for a schema-drift test.
  • History mounts ~3 full-table scans (granularity max, records, daily totals all walk every event in JS). Correct at demo scale; at 100k+ events it needs SQLite-side aggregation or maintained rollups — matching Sol's "profile before materializing" note.

Test gap

Per AGENTS.md, "tests follow the code" — but the repository layer has zero tests, and it is the largest pure-logic surface in the app (bucketing, streaks, records, share math, the fixed-Y max, quota grouping). It is also exactly where the mirror-drift risk (duplication item 2) lives. A repository.test.ts with an in-memory SQLite (or pglite-fixture) harness would close both gaps at once.

Rendered app — re-verified this session

  • Dashboard: one-card-per-subscription (Codex with Session 5h + Weekly rows inside), humanized "GLM Coding Plan", monochrome meters, machine freshness strip — all rendering per spec.
  • History: contribution grid on 120-day demo data with the growth curve clearly visible, records (biggest day / 97d streak / priciest session), ranked top-5 with "… show more (2)" expanding to all 7 models, single window selector, fixed Y ceiling.
  • Explore / Machines / Settings: verified in earlier passes — add-machine sheet with prefilled command, − confirmation dialog, appearance toggle, About detail.
  • Logcat: zero fatal exceptions across every session. The one toast observed — "Error from the WebSocket connection" — is the Metro dev-socket dropping when the USB tunnel re-established after the phone reconnected; the app kept rendering from SQLite through it. Dev-only noise, and exactly the stale-while-revalidate design working as intended.

Recommended fix order

  1. B1 — SQL-only, real correctness bug (small commit: fix(supabase): quota freshness filters errors).
  2. B2 — preserve preference keys across resets (small: fix(mobile): keep preferences across cache resets).
  3. Duplication 1+2 + test gap as one consolidation commit: refactor(mobile): single event bucketing + repository tests.
  4. Hygiene sweep for C-items and dead code in one pass: chore: dead exports, pin dedup, quota key scheme.
