burn — sync latency deep dive

Where fetch time goes on the machine → Supabase → phone path, and a ranked list of optimizations. Grounded in a read of the full pipeline: reporter/daemon (apps/reporter/src), the exporter (crates/burn-events), the wire layer (packages/sync-api/src/supabase.ts), the RPCs (supabase/migrations/0002_api.sql, 0005), and the phone's pull path (apps/mobile/src/lib). No code was changed for this document.

2026-09-06 scope: machine → server → phone freshness analysis only — no code changes companion to docs/mobile-performance-audit.md (on-device rendering, not covered here)

TL;DR

The wire protocol is already right — revision-keyed deltas with the 0005 index, a 1h overlap window, parallel event/quota pushes, and a 6s phone follow-up loop. End-to-end latency is dominated by two costs that are not network costs:

  1. The daemon's hardcoded 30s poll of sync_requests — on average 15s of pure waiting before the machine even notices a phone request (commands.ts:371).
  2. The exporter's full rescan on every cycle — every push re-parses all client history (~12s at 27k records, growing linearly) just to emit the last hour of events (main.rs:141 vs the filter at :168).

Fixing those, plus caching per-process version spawns and one SQL nit, takes a manual pull-to-refresh round trip from ~20–45s today to ~8–15s — without touching any D-decision. A further upstream change (parse only files modified since the cursor) makes the "fresh data exists" case proportional to new data instead of to total history.

Recommendations, ranked

quick win1. Cut the daemon poll to 10–15s

burn_poll_sync_requests is one token check + a tiny select/update (0002_api.sql:243-274). Polling every 10s — even 5s — is noise for a free-tier Supabase project. This alone removes ~10s of average wait and is a one-line change (plus making it configurable, e.g. pollSeconds in BurnConfig). Zero correctness risk.

quick win2. Cache version probes per process

The daemon is long-lived, but every heartbeat/push re-spawns bun x tokscale@pin --version (commands.ts:270,332) and burn-events --version (exporter.ts:49-57). Both binaries are fixed for the process lifetime — resolve once, cache the string. resolveRunner/resolveExporter already cache the runner choice; the remaining spawn per call is what costs. Free ~1–3s per cycle.

quick winserver3. Fix the idle-pull has_more count

When nothing changed, burn_fetch_delta returns an empty events array, so v_max_rev is 0 and has_more executes select count(*) from usage_events where revision > 0 — a full-index count of the entire table, on every phone poll, every active minute (0002_api.sql:315). Replace with exists(select 1 …). Trivial, and it removes a per-minute O(n) server cost that grows with history. One new migration line.

structural4a. Skip the rescan when nothing changed (fingerprint skip)

Every cycle re-parses all history to emit ~1h of events. Add a cheap fingerprint pass to burn-events:

  • burn-events --check stats the client data dirs (mtime + size, ~50ms, no parsing) and prints a stable hash.
  • The reporter caches the hash; on the next cycle it runs --check first and skips the full scan + push entirely when the hash is unchanged.

Idle cycles drop from ~12s CPU+disk to ~50ms + two small RPCs. This matters more than it looks: scan time grows linearly with history (27k today; years of Claude Code sessions could be minutes), so without it the 10-min cron eventually cannot keep up — the scan would outlast the interval.

The subtle part — failed-push invalidation. The skip is safe because an unchanged file set means everything in it was already pushed, regardless of the --since-ms window. But if a push fails after a scan, the cursor does not advance (commands.ts:261) — and a naive hash cache would make the next cycle report "nothing changed", push 0 rows, advance the cursor, and silently drop the un-pushed events until the next file change re-triggers a scan (whose window no longer includes them). Rule: the reporter must clear its cached hash whenever a push fails, so the next cycle rescans. Add a regression test for exactly this sequence: scan → failed push → rescan → same events re-emitted.

D2-safe by construction: the fingerprint decides whether to invoke tokscale's pipeline — it never reimplements provider parsing. Worth a quick grep of ScannerSettings in reference/tokscale first, in case upstream already exposes something exploitable.

structuralupstream4b. Parse only what changed (the deeper fix)

The fingerprint skip makes idle cycles free, but a cycle with new data still pays a full-history scan. The complete fix is pushing --since-ms down into tokscale-core: client files are append-only JSONL/SQLite, so files untouched since the cursor can be skipped entirely, making scan cost proportional to new data. This is upstream-PR territory and pairs naturally with the intended tokscale events --jsonl PR that eventually replaces the exporter binary (D2). Until then, 4a is the local, immediate win.

quick win5. Fold the heartbeat into the push

burn_ingest_events and burn_push_quota_snapshot already set last_heartbeat_at = now() and last_success_at = now() (0002_api.sql:97-103, 234-236) — so the standalone heartbeat RPC before every push (commands.ts:330-335) is a redundant serial round trip. Keep it only as a low-frequency liveness beacon (e.g. every Nth poll, or once per scheduled interval) for machines with nothing to push.

quick win6. Parallelize batch ingest

pushEvents sends 500-row batches serially (commands.ts:251). Fine for the 1-hour overlap window (1–2 batches), but a --full correction pass at 27k rows is 54 sequential RTTs ≈ 15–25s of upload. 3–4 batches in flight cuts that to ~4–6s. Parallel is safe: each batch bumps its own revision server-side, and the phone loops until has_more is false, so interleaved revision commits resolve on a later page.

quick winphone7. Backfill page and chunk sizing

First-sync only, but the most visible "slow" moment a new user feels:

  • fetchDelta defaults to p_limit = 5000 with MAX_PAGES = 8 (supabase.ts:267, sync-cloud.ts:13) — a 27k backfill is 6 sequential ~2–3MB round trips. Pushing toward the server's 20,000 cap during backfill (when hasMore is driving) halves the trips.
  • The 32-row insert chunk (sync-cloud.ts:81-90) means 157 awaited statements per page. The comment itself notes expo-sqlite's bundled SQLite allows ~32k parameters — 500-row chunks (14,000 params) are safe and mean 15× fewer bridge calls. Keep a guard comment updating the binding math, as the current one does.

config8. Supabase region — the fixed multiplier

Every hop in the budget table is multiplied by RTT. If the project is not in a region near the phone (Mumbai / ap-south-1 for this user), each refresh pays 200–300ms across ~6–8 serial round trips, in both directions. A region cannot be changed after project creation — so this is documentation work: say it in the init output, doctor, and the Supabase README ("create the project in the region nearest your phone"). Biggest single fixed-cost win for BYO users, and it is free.

later9. Supabase Realtime as the rendezvous

A broadcast channel on the user's own Supabase would wake the daemon in ~1s instead of the poll interval. It is D3-compatible only if the realtime client lives inside packages/sync-api, and D12-compatible since it is the user's own project. But it adds a persistent websocket per machine and a new failure surface, and the 10s poll already captures ~90% of the win for ~zero complexity. Trade-off to note if ever built: a public broadcast channel is writable by anyone holding the anon key — spam-able "sync requested" messages, which are harmless after 4a (a no-change cycle costs ~50ms). Park unless recommendation 1 proves insufficient.

config10. Spend the savings: tighten the scheduled floor

After 4a, an idle cycle costs ~50ms of exporter work plus a few small RPCs — which makes intervalMinutes: 10 → 5 (or even 3) essentially free. Passive staleness drops from ~11 min to ~6 min without any new machinery. Do this after the scan-skip lands, not before, or you pay the full rescan twice as often.

The honest framing: the scan is only removable when nothing changed. When data exists, 4a still rescans — that is exactly the moment the work is worth doing. 4b is what makes the "user just used tokens and pulls to refresh" case fast.

What is already right — do not touch

  • Revision-based deltas (D5) with the 0005 (revision, event_id) index — the pull itself is a single indexed query; not the bottleneck.
  • The 1h overlap window (events.ts:187) — re-upserts are server-side no-ops that never advance the phone's watermark; the correctness mechanism is sound.
  • Parallel events/quotas within a cycle (commands.ts:289) and independent failure handling.
  • The 2-minute/6s bounded follow-up (refresh.ts) — this closed the earlier audit's "refresh finishes before a machine pushes" finding; it covers the 30s poll plus upload with margin.
  • Dashboard-triggered requestSync (DashboardScreen.tsx:56) — the eager path covers casual pull-to-refresh, not just the Machines tab.
  • Phone→server direction — burn_request_sync is one cheap RPC; it is not part of the problem.

Suggested order

  1. #1 poll 10s — minutes; halves average wait.
  2. #2 cache version strings — minutes; kills a per-cycle spawn.
  3. #3 has_more exists — minutes; one migration, removes per-minute O(n) server work.
  4. #5 fold heartbeat — small; one less serial RTT per cycle.
  5. #4a fingerprint skip — the structural fix. Exporter --check + reporter-side hash cache + the failed-push invalidation rule + a regression test for scan → failed push → rescan.
  6. #10 tighten interval to 5 min — only after #4a.
  7. #8 region documentation — init/doctor/README note.
  8. #6 parallel batches, #7 backfill sizing — mechanical; matter for --full passes and first sync respectively.
  9. #4b upstream pushdown — ride the tokscale events --jsonl PR when it happens.
  10. #9 Realtime rendezvous — only if the 10s poll ever feels slow.

Validating it

Instrumentation mostly exists: the daemon already logs cycle duration (commands.ts:344) and the exporter prints scanned/emitted counts with elapsed time on stderr (main.rs:190-193). What is missing is an end-to-end number: log, on the phone, the interval between request_sync and the first delta pull containing an event newer than the request — that single timestamp is the metric this whole document optimizes. Before/after that number on a real machine is the acceptance test for items 1–5.
