Executive conclusion

Your report establishes a coherent product direction: a BYO Supabase deployment receives incremental usage from an npm-installed reporter on each environment; an Expo Android app reads and caches that data; the app ships by GitHub Release rather than Play Store. I accept this direction and withdraw my earlier preference for direct phone-to-machine pulls and native Kotlin.

The remaining issues are implementation contradictions rather than a different product vision:

  1. A ten-minute scheduled process cannot react eagerly to a phone-written sync_requested flag. Near-immediate refresh needs a resident listener or a clearly bounded delay.
  2. Tokscale’s public CLI does not currently export raw per-message usage rows. “Wrap the existing CLI only” and “store raw per-message rows” cannot both be true without a small Tokscale export addition.
  3. Bucketing all history in the phone’s current timezone will reshape historical calendar days when the phone changes timezone. The report’s claim that travel will not reshape charts is incorrect.

There are also two design corrections that do not require the user to choose a product direction: Supabase access needs real read/write scoping rather than anonymous table reads, and privacy-preserving pseudonyms need a plan for readable workspace/session drill-downs.

Facts verified against the environment

Real Tokscale surface

I ran npx tokscale@latest through its non-interactive JSON commands and opened its TUI. On the current CachyOS environment it discovered active Codex, OpenCode, Pi, and ZCode histories. It did not discover a subscription-quota provider in usage --json on that environment.

The current TUI declares these views: Overview, Usage, Models, Daily, Hourly, optional Minutely, Monthly, Sessions, Stats, and Agents. See reference/tokscale/crates/tokscale-cli/src/tui/app.rs:60.

The reusable normalized record is UnifiedMessage: client, model, provider, session, workspace identity/label, UTC timestamp and derived date, input/output/cache-read/cache-write/reasoning tokens, cost and cost provenance, duration, message count, agent, deduplication key, title, turn marker, and attribution-conflict marker. See reference/tokscale/crates/tokscale-core/src/sessions/mod.rs:69.

Current public export shapes

  • Default --json: aggregate rows grouped by client/model (or another requested grouping), including performance and token buckets.
  • graph: summary, years, daily contributions, per-day client/model breakdown, token buckets, and time metrics.
  • monthly --json: monthly aggregate rows.
  • hourly --json: hourly aggregate rows; the current public shape does not include every internal field.
  • time-metrics --json: total active/wall time, longest continuous activity, maximum concurrency, and session count.
  • usage --json: successful live quota snapshots; failures/absence require separate diagnostics if the app must explain them.
  • report --json: task-attributed report output, not a general raw-message event feed.
Consequence: Burn can achieve aggregate parity by invoking several existing commands, but it cannot achieve raw per-message storage, one-pass collection, complete diagnostics, and full Tokscale-field parity through tokscale report --json alone.

Correction 1 — sync rendezvous needs a listener

CorrectionThe questionnaire combines these behaviours:

  1. Each reporter runs every ten minutes through cron or Task Scheduler.
  2. The phone writes sync_requested.
  3. An online reporter responds eagerly.

The first two do not produce the third. A scheduled reporter cannot see a new flag until its next scheduled run. Writing a flag adds no immediacy when the same job was already going to push on that schedule.

Recommended resolution

Keep scheduled push as the reliable baseline and add an optional resident mode:

burn-report daemon
  ├─ maintains a lightweight control subscription/poll
  ├─ observes a newer sync-request generation
  ├─ runs one coalesced collection/upload job
  ├─ publishes heartbeat + completion/error state
  └─ performs a scheduled fallback push every 10 minutes

The app should never present one global blocking refresh. It renders SQLite immediately, creates one sync request, and updates machine cards independently as new backend revisions arrive. Offline reporters remain stale. Multiple taps coalesce through a monotonically increasing request generation rather than queueing duplicate scans.

User decision 1: choose between near-immediate online-machine refresh through a resident daemon, or schedule-only synchronization with up to ten minutes of expected staleness.

Sol recommendationResident daemon plus scheduled fallback. It matches the already-locked rendezvous UX. If maintenance simplicity wins instead, remove the promise of eager refresh and label the button “Check for updates.”

Correction 2 — raw message rows require a Tokscale export seam

ContradictionD2 selects “wrap existing Tokscale CLI; reimplement nothing.” D5 selects “raw per-message usage rows.” The internal Rust library has the records, but the current stable CLI exports aggregates rather than a complete stream of those records.

Recommended resolution

Preserve the TypeScript reporter and every Tokscale parser, but create a narrow native export seam. Preferred order:

  1. Contribute an upstream Tokscale command such as tokscale events --jsonl with a versioned schema and incremental/cache support.
  2. Until accepted upstream, maintain the smallest possible pinned patch or companion Rust binary that calls tokscale-core and emits the same contract.
  3. Have burn-report invoke that native exporter, validate every row, manage the local cursor, and upload batches.

This is not parser reimplementation. It exposes data Tokscale already normalizes. The patch should remain deliberately boring: no Burn backend code in Tokscale, no Supabase dependency, and no mobile assumptions—only a stable local data export.

A first prototype may invoke graph, models, hourly, time-metrics, and usage, but that is a tracer implementation rather than the final ingestion architecture. It will rescan repeatedly, duplicate concepts across payloads, and still omit some internal fields.

User decision 2: choose aggregate-only ingestion through today’s public CLI, or raw normalized event ingestion through a small pinned/upstream Tokscale export addition.

Sol recommendationChoose the export addition. Full v1 analytics, durable incremental synchronization, future rollups, and honest “whatever Tokscale sees” parity justify this small seam.

Correction 3 — timezone semantics

CorrectionStoring UTC plus the source offset is correct. Re-bucketing in the phone’s current timezone is also technically possible. However, the latter necessarily changes historical day boundaries when the phone’s timezone changes. An event near midnight can move to a different calendar day after travel.

Recommended row fields

  • occurred_at_utc: authoritative instant.
  • source_offset_minutes: offset observed when the event was recorded.
  • source_timezone: IANA zone when discoverable.
  • source_local_date: optional audit value matching the source/Tokscale view.

The app should own a persisted reporting_timezone. Initialize it from the phone during setup, then keep it stable until the user changes it. A later “Use device timezone” mode can explicitly advertise that it re-buckets history.

User decision 3: decide whether travel should reshape all historical calendar buckets.

Sol recommendationFixed, configurable reporting timezone; default Asia/Kolkata for this deployment. Preserve UTC and source offset so alternate views remain possible.

Security correction — scope access instead of opening tables

CorrectionA Supabase publishable key is intended to be present in clients; it is not an access secret. RLS can provide read-only anonymous access, but without an authenticated/scoped identity it cannot distinguish the owner from any other caller who has the project URL and publishable key. That is weak even for a BYO single-user deployment.

Required security properties

  • The Android app receives a read-scoped deployment credential and stores it in Expo SecureStore.
  • Each reporter receives a write-scoped credential; compromise of one reporter does not grant arbitrary database administration.
  • Base tables reject direct anonymous reads and writes.
  • Provider OAuth tokens, API keys, Tokscale auth files, and the Supabase administrative/service credential never enter the APK.
  • Credential rotation can revoke one phone or reporter without deleting usage data.

The exact Supabase implementation can be selected during the spec: authenticated RLS, narrowly scoped RPC/Edge Functions with separate read/write tokens, or an equivalent pattern. “No central Burn account” remains intact; any identity belongs to the user’s own backend.

Suggested v1 bias: optimize onboarding only after the secure permission boundary works. A BYO setup wizard can generate and transfer scoped credentials by QR; this is preferable to treating a service-role key as a general reporter API key or allowing anonymous table reads.

Privacy correction — pseudonyms versus useful drill-downs

The questionnaire accepts both of these:

  • Only numeric metadata and pseudonymous workspace/session identifiers leave machines.
  • v1 includes workspace drill-down and a sessions list.

Those screens will be technically functional but unpleasant if every row is an opaque hash. Resolve this explicitly in the spec:

ModeCloud contentMobile UX
Strict pseudonymousHashes onlyUser-created local aliases; new phone must recreate them.
Readable metadataWorkspace/session labels in plaintextBest UX; BYO owner’s server can read labels.
Encrypted labelsHashes plus ciphertextBest privacy/UX balance; reporters and phone share an encryption key.

Sol recommendationNumeric rows and identifiers remain plaintext for SQL aggregation; optional human labels are end-to-end encrypted with a deployment key shared during setup. Prompts, responses, file contents, and full paths remain excluded.

This can be treated as a fourth user decision if GLM’s original “A” answer explicitly meant that no readable labels may ever leave a machine. If “A” meant “usage metadata but no conversation content,” encrypted labels satisfy the intent without reopening the question.

Sync contract recommendations

Identity and deduplication

Every normalized usage event needs a stable event_id derived from the environment ID, client, and Tokscale/upstream deduplication identity. Avoid including mutable calculated fields such as cost or model attribution in the primary identity; parser/pricing corrections must update the same event rather than create a duplicate.

Where a provider lacks a stable upstream key, the exporter should define and version a deterministic fallback from session identity, event timestamp, and source-local ordinal. Collision handling belongs at the Tokscale adapter boundary.

Incremental changes

Use synchronization revision rather than event time as the mobile watermark. Old events may be corrected after a parser or pricing upgrade. One successful reporter batch creates a monotonically increasing environment revision; every inserted or updated row carries it. The phone asks for revision > last_revision and advances its cursor only after one SQLite transaction commits.

Missing source files should not silently delete historical usage. Preserve ingested history by default. Explicit rebuild/purge operations may emit deletion tombstones so every cache converges intentionally.

Money

Avoid floating-point money in the synchronization schema. Tokscale calculates with f64, but Burn should serialize a decimal string or fixed integer unit and store Postgres numeric. Preserve cost_source and completeness so the UI can distinguish provider-reported spend, estimated API-equivalent cost, zero-priced/free models, and incomplete pricing.

Quota

Quota snapshots are not historical token events. Store them separately with provider, stable account key when available, plan metadata, metric/window label, used/remaining percent, reset time, credit/spend controls, fetched time, source environment, success/error state, and schema version. The app selects the freshest successful snapshot per reliable provider-account identity while retaining diagnostics from failed environments.

Mobile implementation thoughts

Expo is a sound choice because the app is mostly networking, SQLite, filters, and charts. T3Code is useful as a pattern source, not a dependency template.

  • Use React Navigation native-stack and adaptive layouts.
  • Use Expo SQLite in WAL mode; all screens query local data rather than waiting on Supabase.
  • Use Expo SecureStore for scoped backend credentials and encryption keys.
  • Keep synchronization and chart shaping as pure, separately tested modules.
  • Represent partial sync honestly per environment. One failed reporter cannot mark the combined dashboard fully fresh.
  • Virtualize sessions and workspace lists; query by page rather than loading the event corpus into JavaScript memory.
  • Compute chart rollups in SQL or worker/native-friendly paths, not repeated React renders.
  • Use semantic color tokens and dark/light themes. Avoid continuously repainting animations.
  • Benchmark chart-library APK and frame-time cost before committing. Burn does not need T3Code’s heavy native modules.

Reporter implementation thoughts

  • burn-report doctor verifies Node/runtime compatibility, pinned Tokscale availability, exporter schema, config permissions, backend connectivity, write scope, clock/timezone, and scheduler/daemon health.
  • burn-report push performs one idempotent incremental batch and exits with machine-readable diagnostics.
  • burn-report usage refreshes quota snapshots separately from historical ingestion.
  • burn-report daemon is required only if user decision 1 chooses eager rendezvous.
  • burn-report install-service may later generate systemd-user and Windows Task Scheduler/service configuration; manual commands remain documented.
  • Config follows XDG on Linux/WSL and the proper application-data directory on Windows rather than hardcoding ~/.config everywhere.
  • The reporter stores no provider credentials. It lets Tokscale discover existing local credentials and sends only normalized usage/quota output.
  • Every upload reports reporter version, Tokscale version, export schema, parser generation, timezone evidence, scan scope, and completion status.

What GLM should do next

  1. Ask the user only the three numbered decisions above, plus the label-privacy decision only if their previous answer truly excludes encrypted readable labels.
  2. Update the decision record so the synchronization trigger, Tokscale export boundary, timezone semantics, and permission model are internally consistent.
  3. Produce one implementation specification containing the domain model, versioned wire contracts, Supabase schema/policies or scoped API, reporter commands/lifecycle, mobile screens/states, phased build order, and acceptance tests.
  4. Mark the planning phase complete only when every v1 screen can be traced to stored fields, every stored field has an authoritative producer, every sync transition has an offline/failure outcome, and every credential has an explicit scope and storage location.
Completion test: the final spec must explain—without hand-waving—how a phone refresh reaches an online reporter, how a raw event leaves Tokscale, how an old corrected event reaches a phone whose watermark is newer than the event timestamp, how travel affects day buckets, and who can read/write each backend resource.
