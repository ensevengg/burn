Decision record (TL;DR)

#DecisionChoice
D1Data flowMachines push on schedule (cron / Task Scheduler, 10 min + run-on-wake catch-up) to a cloud store; phone reads the store. Phone flipping a sync_requested flag triggers eager pushes (rendezvous pattern). Tailscale direct-pull deferred to v2.
D2Parser sourceWrap tokscale CLI (tokscale report --json, tokscale usage --json); reimplement nothing. Version pinned, Renovate bumps, JSON schema validated before push.
D3BackendSupabase (Postgres + RLS) as implementation #1, behind a thin SyncApi module so PocketBase / self-hosted VPS can be swapped in later.
D4Hosting modelBYO backend — each open-source user pastes their own Supabase URL + keys in a first-run setup screen. No hosted instance, no accounts in v1.
D5Uploaded granularityRaw per-message usage rows, idempotent upserts keyed for dedup. Phone fetches incrementally from its last watermark; machines push only new rows since their cursor.
D6Quota dedupQuota is account-level; every machine may report it, app shows the freshest report per provider-account with a staleness indicator.
D7Reporter packagingTypeScript CLI on npm, run via npx burn-report push; config at ~/.config/burn/reporter.json; burn-report doctor self-check.
D8Keys & securityMachines hold the Supabase secret key (write); phone uses the publishable key with read-only RLS. Full auth only if ever multi-tenant.
D9Android stackExpo SDK 57 / React Native 0.86 / React 19 (New Architecture), following t3code's mobile stack patterns.
D10TimezoneStore UTC + machine-local offset per row; phone buckets days/months/years in its current timezone at render time.
D11v1 scopeAll screens day one: dashboard + limits, daily/monthly/yearly charts with model/agent stacking, cost view, per-machine, per-workspace, sessions list, settings.
D12DistributionRepo burn, APKs via GitHub Releases (EAS build). No Play Store — decided firmly.

Research facts established (agent findings)

tokscale Rust-core CLI (crates/tokscale-core) supporting ~50 AI clients by reading their local files — e.g. Claude Code ~/.claude/projects/*.jsonl, OpenCode ~/.local/share/opencode/opencode.db, Codex ~/.codex/sessions/, ZCode ~/.zcode/cli/db/db.sqlite. Pricing via LiteLLM data with tiered + cache-discount support. Day bucketing via bucket_tz (machine-local). Key commands: report --json, usage --json, --group-by workspace,model, --merge-worktrees. MIT-licensed; distributed via npx with per-platform binaries.

codex "sync" mystery Solved in source: session/token data is local per machine (~/.codex/sessions/). The cross-machine "synced" numbers the user saw are the quota view: tokscale reads the OAuth token from ~/.codex/auth.json and calls OpenAI's account-level endpoint https://chatgpt.com/backend-api/wham/usage (see crates/tokscale-cli/src/commands/usage/codex.rs:260). Consequence: sessions need no cross-machine dedup; quota dedupes by freshness per account.

t3code mobile stack Expo SDK 57, RN 0.86, React 19, @react-navigation native-stack, Clerk auth, expo-sqlite + expo-secure-store, Uniwind (Tailwind for RN), Effect-based shared workspace packages, EAS builds with CNG prebuild, Nitro native modules. Borrowed for stack patterns; the app itself is unrelated.

tailscale free tier Personal plan: free at 6 users, unlimited user-owned devices (old 3-user/100-device caps removed, 2026 pricing update). MagicDNS, ACLs, subnet routing included; 180-day device key expiry is the main annoyance. Sources: tailscale.com/pricing, free plans doc, pricing-v4 blog. Verdict: fine for 1 user / ~4 devices; also already planned for T3code remote access. Headscale exists as the self-hosted escape hatch.

self-host cloud options Ranked for the "own server someday" goal: (1) self-hosted Supabase via Docker on a VPS (Hetzner ~€4/mo) — zero app changes; (2) PocketBase — single ~15MB Go binary, SQLite, REST + auth + realtime, Raspberry-Pi-capable; (3) raw VPS + Postgres + thin API; (4) Fly.io/Railway. The SyncApi abstraction (D3) is what keeps all four reachable.

Round 1 — data flow, parser, backend, granularity, quotas

❓ Q1 — Data flow: push or pull?

User Machines pushing is better, I think. What do you say? Or we do a refresh on mobile, it sends a signal to every available machine, and they send the data over. This also seems nice. If a machine is not active, we show that and of course we store and keep piling onto the data we have loaded since previous runs. Also asked: what are the cloud options for my own server? What kinds of cloud?

Agent notes Merged the user's two instincts: scheduled push is the backbone (NAT makes phone→machine pulls impossible on cellular), and the user's "phone signals machines" idea ships as the rendezvous pattern — the phone flips a sync_requested flag in the central store; each machine's job (10-min cron + run-on-wake catch-up so sleep-missed runs don't vanish) pushes eagerly when it sees it. Machines that are offline show "last synced Xh ago" — exactly the staleness display requested. Data accumulates via idempotent upserts, so nothing is refetched or lost. Tailscale direct-pull accepted as v2 bolt-on (user confirmed free-tier worries resolved: 6 users / unlimited devices). Cloud options for the own-server future documented above.

❓ Q2 — Wrap tokscale or reimplement parsers?

User Do tokscale then, I guess. It does seem a lot of work to implement providers, especially if someday a new one pops up. My only question: how often do we update the tokscale implementation inside this, depending on when tokscale itself gets updated?

Agent notes Clarified the update question: tokscale never ships inside the app — it runs on machines, so "updating" is just the reporter's version pin. Policy: pin a known-good tokscale version, Renovate bumps weekly, and the reporter validates the JSON shape before pushing so an upstream schema change fails loudly on the machine instead of silently corrupting the DB. @latest stays available for manual runs.

❓ Q3 — Backend: Supabase, Convex, or Firebase?

User Sure then, Supabase I guess. I recommended Convex since a lot of people I know use it and a few great YouTubers mentioned it.

Agent notes Supabase wins on substance here: Postgres group-bys do the daily/monthly/yearly rollups, RLS secures the BYO model, free tier is ample for MB-scale data, and self-hosting keeps the open-source story clean. Convex's DX reputation is deserved but its aggregation is JS-side and the runtime is lockier. With the SyncApi abstraction the choice stays reversible anyway.

❓ Q4 — Open-source hosting model

User BYOK. I really do want to implement my own server someday, hence in Q1 I'm asking it.

Agent notes BYO confirmed twice now — this is the strongest signal in the whole interview. It directly mandates the thin SyncApi data-layer module (see Q8) so "own server someday" is a weekend swap, not a rewrite.

❓ Q5 — Uploaded granularity

User B sure, plus we stack, so we can have it so that the already available data in the DB is not fetched again, hence saving memory too. All fetch from the last update.

Agent notes Raw per-message usage rows confirmed, with incremental sync made explicit as a requirement in both directions: machines keep a cursor and push only new rows; the phone fetches from its last watermark and mirrors the schema in local expo-sqlite. Upsert keys make every push idempotent, so "fetch from the last update" can never double-count.

❓ Q6 — Quota reporting across machines

User Only my Codex is shared across Windows, WSL and CachyOS, I think. I don't use Claude, zai is different. So yeah, no issues with shared quota cuz it will be the same.

Agent notes Confirmed by source later (see codex fact box): shared-sub quota is account-level and identical from any machine, so freshest-wins dedup per provider-account is correct and trivially safe. Session rows remain per-machine with no dedup needed. NOTE for spec: WSL and Windows are the same physical machine — worth giving each reporter a distinct machine_id (e.g. windows / wsl) while knowing they share hardware; also consider a machine-level "same host" grouping in the per-machine screen.

❓ Q8 — Backend abstraction now or later?

User Sure, we go for a process which takes less time for maintenance and changes later down the line.

Agent notes Thin SyncApi from day one, on both sides: the phone has one module for all reads, the reporter has one for all writes. Supabase becomes implementation detail #1; PocketBase/own-server #2. Slightly more code now, drastically cheaper maintenance later — the user's stated priority.

❓ Q9 — Expo/React Native vs native Kotlin?

User Expo then, I guess.

Agent notes Expo SDK 57 / RN 0.86 / React 19 chosen. Native Kotlin was the smaller-APK (~4–6MB vs ~20–25MB) / faster-cold-start option, but Expo wins on the user's other priorities: iOS-someday is nearly free, the TS contributor pool for an open-source project is far bigger, and t3code provides proven patterns for exactly this stack.

❓ Q10 — Timezone and day boundaries

User I think tokscale fetches data as per what the machine's time is set to. I remember misconfiguring time and seeing it reflected in tokscale, then correcting it to see normal time. So dynamic?

Agent notes Confirmed dynamic, and made the semantics precise because of the user's clock-misconfiguration anecdote: machines record UTC + their local offset per row (auditable — a misconfigured clock is visible, not silent), and the phone buckets days/months/years in its current timezone at render time. "Today" is always the user's today; travel never scrambles charts; historical data re-buckets cleanly since everything is UTC underneath. Tokscale's bucket_tz behavior matches the user's observation.

Reconciliation addendum — Sol review (2026-09-05)

Agent notes A second agent ("Sol", GPT 5.6) reviewed this questionnaire, the reference repos, and the real tokscale CLI (sol-thoughts.html). Its three corrections were verified against the tokscale source and accepted, with the user delegating the final calls ("do what you think is best"):

  • Q16 → (a) Resident burn-report daemon (~30s poll of sync_requests) + scheduled fallback. Schedule-only cannot deliver eager refresh — the original rendezvous wording was contradictory and is amended.
  • Q17 → (a) Raw per-message rows require an export seam: tokscale's CLI is aggregate-only (verified: report --json is task-attributed; no session-row export). A small pinned Rust exporter (burn-events) will call tokscale-core and emit versioned JSONL of UnifiedMessage; an upstream tokscale events --jsonl PR is the intended replacement. "Wrap tokscale, reimplement nothing" survives — the seam serializes tokscale's own normalized records.
  • Q18 → (a) Fixed, persisted reporting_timezone (default Asia/Kolkata) instead of dynamic device-tz bucketing. The original claim that travel "won't scramble charts" was wrong; UTC + source offset stay stored either way.
  • Q19 → (a) Plaintext readable metadata (workspace labels, session titles) — consistent with the user's "see quite literally everything"; encrypted-label mode remains a future option via a separate table.
  • Security (no user call needed) The D7 "publishable key + anon-read RLS" model is replaced by scoped tokens: RLS denies all direct table access; all access flows through token-gated burn_api.* security-definer RPCs (read token for the phone in SecureStore, per-environment ingest tokens for reporters, SHA-256-hashed at rest, revocable). No Supabase Auth, no central accounts.

Everything else in Sol's review (revision-based watermarks, numeric money, quota snapshot diagnostics, core tables, information architecture, vertical-slice build order, risk register) is adopted as spec guidance without user decisions.
